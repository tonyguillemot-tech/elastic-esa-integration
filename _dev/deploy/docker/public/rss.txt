          <title>Elastic Cloud Enterprise (ECE) 3.8.3 and 4.0.3 Security Update (ESA-2025-22)</title>
          <dc:creator><![CDATA[ikakavas]]></dc:creator>
          <category>Security Announcements</category>
          <description><![CDATA[
            <p><strong>Elastic Cloud Enterprise Improper Authorizatio</strong>n <strong>(ESA-2025-22)</strong></p>
<p>Improper Authorization in Elastic Cloud Enterprise can lead to Privilege Escalation where the built-in readonly user can call APIs that should not be allowed. The list of APIs that are affected by this issue is:</p>
<pre><code class="lang-auto">post:/platform/configuration/security/service-accounts
delete:/platform/configuration/security/service-accounts/{user_id}
patch:/platform/configuration/security/service-accounts/{user_id}
post:/platform/configuration/security/service-accounts/{user_id}/keys
delete:/platform/configuration/security/service-accounts/{user_id}/keys/{api_key_id}
patch:/user
post:/users
post:/users/auth/keys
delete:/users/auth/keys
delete:/users/auth/keys/_all
delete:/users/auth/keys/{api_key_id}
delete:/users/{user_id}/auth/keys
delete:/users/{user_id}/auth/keys/{api_key_id}
delete:/users/{user_name}
patch:/users/{user_name} 
</code></pre>
<p><strong>Affected Versions:</strong></p>
<p>Elastic Cloud Enterprise versions after 3.8.0 and up to including 3.8.2</p>
<p>Elastic Cloud Enterprise versions after 4.0.0 and up to including 4.0.2</p>
<p><strong>Affected Configurations:</strong></p>
<p>This issue affects all ECE users.</p>
<p><strong>Solutions and Mitigations:</strong></p>
<p>Users should upgrade to version 3.8.3 and 4.0.3. In addition to the upgrade, Elastic Cloud Enterprise users should investigate whether there exist any users or service accounts that have been created by the readonly user and potentially delete them. The <a href="https://github.com/elastic/cleanup-ece-users">following tooling</a> offers this functionality. Elastic advises extreme caution while deleting users, to ensure that only the necessary ones are deleted.</p>
<p><strong>For Users that Cannot Upgrade:</strong></p>
<p>Users that cannot upgrade, should also use the <a href="https://github.com/elastic/cleanup-ece-users">provided tooling</a> to list users or service accounts that have been created by the readonly user and potentially delete them.</p>
<p><strong>Severity:</strong> CVSSv3.1: 8.8(High) CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H}</p>
<p><strong>CVE ID</strong>: CVE-2025-37736</p>

          <title>Elastic Cloud Enterprise (ECE) 3.8.2 and 4.0.2 Security Update (ESA-2025-21)</title>
          <dc:creator><![CDATA[ismisepaul]]></dc:creator>
          <category>Security Announcements</category>
          <description><![CDATA[
            <p><strong>Elastic Cloud Enterprise (ECE) Improper Neutralization of Special Elements Used in a Template Engine (ESA-2025-21)</strong></p>
<p>Improper neutralization of special elements used in a template engine in Elastic Cloud Enterprise (ECE) can lead to a malicious actor with Admin access exfiltrating sensitive information and issuing commands via a specially crafted string where Jinjava variables are evaluated.</p>
<p><strong>Affected Versions:</strong></p>
<p>Versions starting from 2.5.0 up to and including 3.8.1, and versions starting from 4.0.0 up to and including 4.0.1.</p>
<p><strong>Affected Configurations:</strong></p>
<p>This issue can only be exploited by users with access to the Elastic Cloud Enterprise (ECE) admin-console and access to a deployment with the Logging+Metrics feature enabled. By submitting plans with specially crafted payloads it is possible to inject code to be executed and the result to be read back via the ingested logs.</p>
<p><strong>Solutions and Mitigations:</strong></p>
<p>Users should upgrade to version 3.8.2 and 4.0.2.</p>
<p><strong>For Users that Cannot Upgrade:</strong></p>
<p>There are no workarounds</p>
<p><strong>Indicators of Compromise (IOC)</strong></p>
<p>Users can monitor the request logs for malicious payloads, by using the search query:</p>
<ul>
<li><code>(payload.name : int3rpr3t3r or payload.name : forPath)</code></li>
</ul>
<p><strong>Severity:</strong> CVSSv3.1: 9.1 (Critical)  - <a href="https://www.first.org/cvss/calculator/3-1#CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:H">CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:H</a></p>
<p><strong>CVE ID</strong>: CVE-2025-37729</p>

            <p><strong>Kibana Insufficiently Protected Credentials in the CrowdStrike Connector (ESA-2025-19)</strong></p>
<p>Insufficiently Protected Credentials in the Crowdstrike connector can lead to Crowdstrike credentials being leaked. </ul>
<p><strong>Affected Configurations:</strong></p>
<p>Kibana instances using the CrowdStrike Connector</p>
<p><strong>Solutions and Mitigations:</strong></p>
<p>The issue is resolved in versions 8.18.8 or 8.19.5 or 9.0.8 or 9.1.5.</p>
<p><strong>For Users that Cannot Upgrade:</strong><br>
There are no workarounds</p>

          <title>Elasticsearch 8.18.8, 8.19.5, 9.0.8, 9.1.5 Security Update (ESA-2025-18)</title>
          <dc:creator><![CDATA[ismisepaul]]></dc:creator>
          <category>Security Announcements</category>
          <description><![CDATA[
            <p><strong>Elasticsearch Insertion of sensitive information in log file (ESA-2025-18)</strong></p>
<p>Insertion of sensitive information in log file in Elasticsearch can lead to loss of confidentiality under specific preconditions when auditing requests to the <a href="https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-reindex">reindex API</a></p>
<p><strong>Affected Versions:</strong></p>
<ul>
<li><strong>7.x:</strong> All versions from 7.0.0 and up to and including 7.17.29</li>
<li><strong>8.x:</strong> All versions from 8.0.0 and up to and including 8.18.7</li>
<li><strong>8.19.x:</strong> All versions from 8.19.0 and up to and including 8.19.4</li>
<li><strong>9.0.x:</strong> All versions from 9.0.0 and up to and including 9.0.7</li>
<li><strong>9.1.x:</strong> All versions from 9.1.0 and up to and including 9.1.4</li>
</ul>
<p><strong>Affected Configurations:</strong></p>
<p>This affects deployments where all the below are true:</p>
<ul>
<li>
<p>Audit logging is enabled ( <code>xpack.security.audit.enabled: true</code> )</p>
</li>
<li>
<p>Audit logging is configured to contain authentication_success events ( <code>xpack.security.audit.logfile.events.include includes authentication_success</code> )</p>
</li>
<li>
<p>Audit logging is explicitly configured to capture request bodies ( <code>xpack.security.audit.logfile.events.emit_request_body: true</code> ). The default value is <code>false</code>.</p>
</li>
</ul>
<p><strong>Solutions and Mitigations:</strong></p>
<p>The issue is resolved in version 8.18.8, 8.19.5, 9.0.8, 9.1.5.</p>
<p><strong>For Users that Cannot Upgrade:</strong></p>
<p>If the affected configuration is in use:</p>
<p><strong>Self-hosted</strong></p>
<p>Users can set <code>xpack.security.audit.logfile.events.emit_request_body</code> to <code>false</code></p>
<p><strong>Cloud</strong></p>
<p>Users can set <code>xpack.security.audit.logfile.events.emit_request_body</code> to <code>false</code></p>
<p><strong>Severity:</strong> CVSSv3.1: Medium(5.3) CVSS:3.1/AV:A/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N</p>
<p><strong>CVE ID</strong>: CVE-2025-37727</p>

          <description><![CDATA[
            <p><strong>Elasticsearch XML external entity (XXE) injection in Apache Tika (ESA-2025-14)</strong></p>
<p>On August 20, 2025, CVE-2025-54988 in Apache Tika PDF parser module was announced, disclosing an XML External Entity injection flaw in the Apache Tika tika-parser-pdf-module. This vulnerability allows an attacker to provide a crafted XFA file within a PDF, read sensitive data, or trigger malicious requests to internal resources or third-party servers.</p>
<p>This issue affects Elasticsearch, however the severity is reduced from critical to high due to the attacker requiring authentication. Threat actors can trigger the Apache Tika XXE vulnerability in Elasticsearch by providing a malformed PDF to the ingest attachment processor, which can trigger unauthorized requests to internal resources or third-party servers, or could be used to read sensitive data.</p>
<p><strong>Affected Versions:</strong><br>
8.18.0 up to and including 8.18.5, 8.19.0 up to and including 8.19.2, 9.0.0 up to and including 9.0.5, 9.1.0 up to and including 9.1.2</p>
<p><strong>Affected Configurations:</strong></p>
<p>Elasticsearch is affected by this only when using the ingest attachment processor.</p>
<p>For ​​versions of Elasticsearch that use the Java Security Manager, which include 8.17.8 and below, the risk is mitigated as the Java Security Manager prevents the exploitation of the vulnerability.</p>
<p><strong>Solutions and Mitigations:</strong></p>
<p>Users should upgrade to version 8.18.6, 8.19.3, 9.0.6, and 9.1.3.</p>
<p><strong>For Users that Cannot Upgrade:</strong></p>
<p>We <strong>strongly</strong> recommend users to upgrade. The following workarounds will mitigate the security issue but can have a serious impact on data ingestion.</p>
<p>Users that cannot upgrade could delete any ingest pipelines that call the “attachment” processor and handle untrusted PDF files. Note that this can cause ingest to fail or will produce data that has bypassed any enrichment or transformation logic that existed in the deleted pipelines.</p>
<ol>
<li>
<p>Find all pipelines that have an attachment processor with the <a href="https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-ingest-get-pipeline">Get Ingest Pipelines API</a>:</p>
<p><code>GET _ingest/pipeline</code></p>
<p>This will return all pipelines in the system, with the key of each top-level object being the pipeline name.</p>
</li>
<li>
<p>Look for any processors in the result that are labeled “<em>attachment</em>”, and record the pipeline name.</p>
</li>
<li>
<p>Attempt to delete each of those pipelines with the <a href="https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-ingest-delete-pipeline">Delete Ingest Pipeline API</a> to delete the pipeline:</p>
<p><code>DELETE _ingest/pipeline/pipeline1</code></p>
</li>
</ol>
<p>Note that built-in pipelines, like <strong>search-default-ingestion</strong>, cannot be deleted. Calling the Delete Ingest Pipeline API will report success but the pipeline will be immediately recreated.</p>
<p>Also ,attempts to delete some pipelines will fail with an “illegal_argument_exception”  because those pipelines are configured to be the default or final pipeline of an index.</p>
<p>An alternative is to delete the ingest attachment module on each Elasticsearch server, with the impact of any pipeline that uses the attachment processor failing. This means that any pipelines that transform data from various formats like Word, Excel, or PDF files would fail. Customers would not be able to ingest this data. Attempts to do so would get an HTTP response with status code “500”, and a root cause type of <code>illegal_state_exception</code>. This workaround can only be applied on Self-Hosted Elasticsearch Clusters.</p>
<ol>
<li>
<p>On each Elasticsearch node in a cluster, change to the Elasticsearch installations’s top-level directory</p>
</li>
<li>
<p>Delete the ingest attachment module by calling “rm -Rf modules/ingest-attachment"</p>
</li>
<li>
<p>Restart the Elasticsearch server</p>
</li>
</ol>
<p><strong>Severity:</strong> CVSSv3.1: 8.8(High) - CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H/MPR:L</p>

            <p><strong>Kibana privilege escalation via <code>reporting_user</code> role (ESA-2025-13)</strong></p>
<p>Incorrect authorization in Kibana can lead to privilege escalation via the built-in <code>reporting_user</code> role which incorrectly has the ability to access all Kibana Spaces.</p>
<p><strong>Affected Versions:</strong></p>
<p>Kibana versions starting from and including 9.0.0, up to and including 9.0.5; and versions from and including 9.1.0 up to and including 9.1.2.</p>
<p><strong>Affected Configurations:</strong></p>
<p>This issue affects deployments which assign the built-in <code>reporting_user</code> role to end users. This role is not assigned to users by default.</p>
<p>The <code>reporting_user</code> role in affected versions incorrectly grants users the ability to access <strong>all</strong> Kibana Spaces, with the following privileges:</p>
<ul>
<li>
<p>Read access to Discover, including the ability to generate reports.</p>
</li>
<li>
<p>Read access to Dashboards, including the ability to generate reports.</p>
</li>
<li>
<p>Read access to the Visualization Library, including the ability to generate reports.</p>
</li>
<li>
<p>Read access to Canvas, including the ability to generate reports.</p>
</li>
</ul>
<p>The <code>reporting_user</code> role in versions prior to 9.0 did not grant access to any Kibana Spaces; it only granted reporting functionality within the Spaces users were already authorized to access.</p>
<p><strong>Important:</strong> This vulnerability does not violate configured index privileges. Users with the <code>reporting_user</code> role assigned will not have access to any additional user documents or indices. They will be able to access the aforementioned Kibana assets, but not the data within, unless their existing index privileges would otherwise grant access.</p>
<p><strong>Solutions and Mitigations:</strong></p>
<p>The issue is resolved in version 9.0.6 and 9.1.3. Note that versions prior to 9.0.0 are not affected.</p>
<p>Any API Keys created by users with the <code>reporting_user</code> role in the affected versions will continue to have elevated privileges. Ensure these API Keys are <a href="https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-security-invalidate-api-key">invalidated</a> to prevent unauthorized access to additional Spaces.</p>
<p><strong>For Users that Cannot Upgrade:</strong></p>
<p>Administrators should revoke the <code>reporting_user</code> role from their end users, and instead grant access to reporting functionality via custom roles which grant the appropriate access to reporting.</p>
<p><strong>Severity:</strong> CVSSv3.1: 6.5 (Medium) <a href="https://www.first.org/cvss/calculator/3-1#CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N">CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N</a></p>
<p><strong>CVE ID</strong>: CVE-2025-25010</p>

            <blockquote>
<p>Updated: August 29, 2025</p>
<p>Elastic has been directly engaging with the independent researcher. After evaluating additional information provided by the researcher, our original assessment still stands. To confirm we are responsibly assessing this report and providing an unbiased perspective, we are engaging a neutral third-party to review the finding. For users of Elastic Defend, no action is required.</p>
</blockquote>
<p>On August 23rd, Elastic received additional data from the original researcher in the form of crash dumps and a proof of concept (PoC) involving an executable and a kernel driver. Since then, Elastic has been directly engaging with the researcher.</p>
<p>The crash dumps were caused by a known stability issue in the 8.17.0 Elastic Defend driver which was first reported by a customer in April. We take such reports seriously, so we released a fix a week later in versions 8.17.6, 8.18.1, and 9.0.1 on May 6th, one month before the researcher’s initial bug report. A description of the bug is available in our release <strong><a href="https://www.elastic.co/guide/en/security/8.19/release-notes-header-8.17.0.html#bug-fixes-8.17.6">notes</a></strong> (IRQL_NOT_LESS_OR_EQUAL bugcheck). While primarily observed in the presence of Trellix, the bug could be reached through other third-party software or conditions.</p>
<p>The PoC does not reproduce the bug detailed above nor does it demonstrate any new security bugs or vulnerabilities as stated in the researcher's updated blog. Rather, it leverages administrator rights to enable <strong><a href="https://learn.microsoft.com/en-us/windows-hardware/drivers/install/test-signing">test signing</a></strong>, reboot the system, then load a custom unsigned kernel driver. The driver unsuccessfully attempts to modify a non-writable region of our kernel driver's memory at offset 0x120DD using the ExAcquireFastMutex function. Memory page protections block this attempt, resulting in a BSOD/bugcheck with a separate ATTEMPTED_WRITE_TO_READONLY_MEMORY error code. Because the non-writable address resides within our kernel driver’s memory range, the resulting blue screen unfortunately names our driver. With administrator rights being used to load a custom unsigned kernel driver, this approach can be used to target any driver on the system. In summary, the crash resulting from the researcher’s kernel driver PoC was due to a bug in the PoC code, and was unrelated to Elastic Defend.As with all software, we recommend users stay up to date with <strong><a href="https://www.elastic.co/docs/release-notes">release notes</a></strong> and apply updates when they are available. We also recommend users practice least-privilege principals to minimize the prevalence of unnecessary administrator rights and to enable standard mitigations like Secure Boot and Hypervisor-Protected Code Integrity (HVCI). For users of Elastic Defend, no further action is required.</p>
<p>To confirm we are responsibly assessing this report and providing an unbiased perspective, we are engaging a neutral third-party to review the finding. Elastic will continue to investigate any new reports received and provide updates should we discover any valid security issues.</p>
<blockquote>
<p>Updated: August 19, 2025<br>
Elastic has reviewed additional evidence shared in a blog post on August 19th. Our prior assessment stands. For users of Elastic Defend, no action is required.</p>
</blockquote>
<p>On August 16, 2025, Elastic’s Information Security team became aware of a blog and social media posts suggesting an alleged vulnerability in Elastic Defend.</p>
<p>Having conducted a thorough investigation, Elastic’s Security Engineering team has found no evidence supporting the claims of a vulnerability that bypasses EDR monitoring and enables remote code execution. While the researcher claims to be able to trigger a crash/BSOD in the Elastic Endpoint driver from an unprivileged process, the only demonstration they have provided does so from another kernel driver.</p>
<p>Elastic will continue to investigate and will provide updates for our customers and community, should we discover any valid security issues. We request that any detailed information that demonstrates the ability to crash the driver from an unprivileged process be shared with us at <a href="mailto:security@elastic.co">security@elastic.co</a>.</p>
<p><em>Background</em></p>
<p>Elastic values its partnership with the security community. We lead a mature and proactive bug bounty program, launched in 2017, which has awarded over $600,000 in bounty payments.</p>
<p>The security researcher making the claim submitted multiple reports to Elastic claiming Remote Code Execution (RCE) and behavior rules bypass for Elastic EDR. The reports lacked evidence of reproducible exploits. Elastic Security Engineering and our bug bounty triage team completed a thorough analysis trying to reproduce these reports and were unable to do so.  Researchers are required to share reproducible proof-of-concepts; however, they declined.</p>
<p>By not sharing full details and publicly posting, the conduct of this security researcher is contrary to the principles of coordinated disclosure.</p>
<p>The Elastic Secure Software Development Framework (SSDF) ensures Elastic software is developed securely to minimize the security risks to our customers, Elastic Products, and our software supply chain. The framework is aligned with best practices for secure software development, including NIST SSDF, OWASP SAMM, and BSIMM. Our product security testing program requirements include in-house and third-party testing for Software Composition Analysis (SCA), Static Secure Code Analysis (SAST), Dynamic Application Security Testing (DAST), Third-party Pentesting, Red Team Adversarial Attack Simulation, and other tests.</p>
<p>Elastic implements procedures to receive, analyze, respond to, and remediate vulnerabilities disclosed to us from all sources. Vulnerability impact assessments are performed to review and validate security findings, determine if Elastic products are affected, rate the severity, and perform remediation in accordance with the impact.</p>
<p>For issues that have a significant security impact on Elastic products, an Elastic Security Advisory (ESA) is published to notify our users of the issue and remediations. As a CNA, Elastic assigns both a CVE and an ESA identifier to each advisory. Advisories are announced in the <a href="https://discuss.elastic.co/c/announcements/security-announcements">Security Announcements forum</a> and published to Mitre/NVD.</p>

            <h4><a name="p-1434395-beats-uncontrolled-search-path-element-can-lead-to-local-privilege-escalation-lpe-when-using-the-windows-installer-esa-2025-12-1" class="anchor" href="https://discuss.elastic.co#p-1434395-beats-uncontrolled-search-path-element-can-lead-to-local-privilege-escalation-lpe-when-using-the-windows-installer-esa-2025-12-1"></a>Beats Uncontrolled Search Path Element can lead to Local Privilege Escalation (LPE) when using the Windows Installer (ESA-2025-12)</h4>
<p>An uncontrolled search path element vulnerability can lead to local privilege Escalation (LPE) via Insecure Directory Permissions. The vulnerability arises from improper handling of directory permissions. An attacker with local access may exploit this flaw to move and delete arbitrary files, potentially gaining SYSTEM privileges.</p>
<h3><a name="p-1434395-affected-versions-2" class="anchor" href="https://discuss.elastic.co#p-1434395-affected-versions-2"></a>Affected Versions:</h3>
<p>Beats up to and including <code>8.18.5</code>, from version <code>8.19.0</code> up to and including <code>8.19.2</code>, from version <code>9.0.0</code> up to and including <code>9.0.5</code>.</p>
<h3><a name="p-1434395-affected-configurations-3" class="anchor" href="https://discuss.elastic.co#p-1434395-affected-configurations-3"></a>Affected Configurations:</h3>
<p>The issue only affects Beats when installed through the install-service script for Windows. Example when installing <a href="https://www.elastic.co/docs/reference/beats/filebeat/filebeat-installation-configuration#installation">Filebeat </a>using <code>.\install-service-filebeat.ps1</code>.</p>
<p>Note: Elastic Agent is <strong>NOT</strong> affected because the Beats are installed in a different path <code>C:\Program Files\Elastic\Agent</code></p>
<h3><a name="p-1434395-solutions-and-mitigations-4" class="anchor" href="https://discuss.elastic.co#p-1434395-solutions-and-mitigations-4"></a>Solutions and Mitigations:</h3>
<p>The issue is resolved in version 9.1.0.</p>
<p>A maintenance release will be made available for versions 8.18.6, 8.19.3, and 9.0.6.</p>
<h3><a name="p-1434395-for-users-that-cannot-upgrade-5" class="anchor" href="https://discuss.elastic.co#p-1434395-for-users-that-cannot-upgrade-5"></a><strong>For Users that Cannot Upgrade:</strong></h3>
<p>To resolve the issue for users that cannot upgrade, Beats can be uninstalled and re-installed using the install script from a patched version.</p>
<p>Note: Beats keeps its state in the data path. When re-installing Beats, users need to make sure they have permissions to move the Beats data folder to the new location in <code>C:\Program Files</code>. The new installation script will move the data folder. In the event the script fails, the user will need to manually copy the data folder - this is likely due to permission error.</p>
<h4><a name="p-1434395-step-by-step-using-filebeat-as-an-example-6" class="anchor" href="https://discuss.elastic.co#p-1434395-step-by-step-using-filebeat-as-an-example-6"></a><strong>Step-by-step using Filebeat as an example:</strong></h4>
<ol>
<li>Download the latest Filebeat (e.g. 9.1.1)</li>
<li>Start a Powershell as administrator</li>
<li>Stop the Filebeat service: <code>stop-service filebeat</code></li>
<li>Extract the downloaded filebeat: Expand-Archive <code>.\filebeat-9.1.1-windows-x86_64.zip</code></li>
<li>Copy the install script onto the current Filebeat installation: <code>cp .\filebeat-9.1.1-windows-x86_64\filebeat-9.1.1-windows-x86_64\install-service-filebeat.ps1 'C:\Program Files\Filebeat\install-service-filebeat.ps1'</code></li>
<li>Uninstall the Windows service: <code>.\uninstall-service-filebeat.ps1</code></li>
<li>Re-install using the new script: <code>'C:\Program Files\Filebeat\install-service-filebeat.ps1'</code></li>
</ol>
<p><strong>Severity</strong>: CVSSv3.1: 7.0 (High) - CVSS:3.1/AV:L/AC:H/PR:L/UI:N/S:U/C:H/I:H/A:H</p>
